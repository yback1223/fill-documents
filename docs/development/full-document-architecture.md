# 전체 문서 작성 범위와 완료 판정 설계안

작성: 2026-10-08. 상태: 설계 제안, 독립 검토 전. 생산 코드와 기존 검증 기록을 변경하지 않는다.

## 1. 요구와 현재 원인

사용자 확정 요구는 “사용자가 원하지 않은 부분 외에는 모두 채운다”이다. 이번 예시는 형식별로 완전히 작성된 결과 하나만 제공하고, 원본과 작성 예시를 눈에 띄게 구분한다. 임의의 빈칸을 채우는 것이 아니라 문서의 작성 주체가 작성해야 하는 항목을 빠짐없이 처리해야 한다.

| ID | 요구 | 외부에서 확인할 수 있는 성공 조건 |
| --- | --- | --- |
| FD1 | 기본 범위는 문서 전체 | 원본의 모든 본문·표·별첨·부록 작성 대상이 목록에 있고, 표식이 없는 칸도 누락하지 않는다. |
| FD2 | 필드 처리와 전체 완성 구분 | `ok: true` 또는 표식 0개만으로 전체 작성 완료라고 보고하지 않는다. |
| FD3 | 사실을 만들지 않음 | 실제 문서에서 미확인 이름·금액·날짜·등록번호·승인·서명을 사실처럼 채우지 않는다. 필요한 사실과 작업 제약을 분리해서 알린다. |
| FD4 | 가상 예시는 끝까지 일관되게 작성 | 문서 목적에 맞는 단일 가상 설정으로 모든 적용 항목을 채운다. 예산 합계·단위·일정·인원·기관명 등 문서 사이 값이 일치한다. |
| FD5 | 형식 유지와 확장 | 새로 포함된 표·부록도 기존 보존·넘침 검사를 지키고, 내용 누락을 줄이려고 글씨를 몰래 축소하거나 내용을 자르지 않는다. |
| FD6 | 결과 하나와 분명한 비교 | HWP/HWPX/DOCX/PDF마다 원본 하나와 작성 예시 하나를 제공한다. 합본의 모든 페이지에 원본/가상 작성 예시 구분을 보이고 목차·책갈피로 연결한다. |

코드에서 확인한 현재 동작:

- `lib/engine.mjs:28–41`: `inspectDocument`는 adapter가 발견한 필드를 정규화한다. 원본의 일반 빈칸과 표 전체를 조사하지 않는다.
- `lib/engine.mjs:69–90`: 발견 필드에 `checkValues`를 적용하고 adapter의 보존 검사를 통과하면 새 파일을 발행한다. 문서 전체 작성 범위는 판정하지 않는다.
- `lib/fields.mjs:6–21,25–50`: “모든 필드 필수”는 **이미 발견된 필드 목록**에만 적용된다. 그 밖의 미작성 칸에 대한 보장이 아니다.
- `lib/adapters/docx.mjs:88–114,144–149`: 지원되는 문서 부분의 `{{name}}`를 수집한다. 표식 없는 표의 빈 셀은 작성 대상으로 발견하지 않는다.
- `lib/adapters/hwpx.mjs:26–64,117–122`: 누름틀/표식을 수집하며, 프로필이 있으면 지정 반복 영역을 추가한다.
- `lib/adapters/hwp.mjs:28–50,66–84`: 고유한 최상위 표식 문단을 대상으로 한다. 셀 편집의 일반 지원을 의미하지 않는다.
- `lib/adapters/pdf.mjs:223–230`: 지원되는 AcroForm 필드를 대상으로 한다. 빈 서명 필드와 정적 본문의 빈칸은 작성 목록과 다르다.
- `bin/fill-documents.mjs:84`: 예외가 없으면 `ok: true`를 출력한다. 현재 SKILL의 5단계는 이를 생성 성공의 기준으로 쓰지만, 별도의 전체 완성 기준이 없다.
- `tests/core.test.mjs`는 발견 필드 누락·공백·미지 키를 검사한다. `tests/office-pdf.test.mjs`의 표식 없는 DOCX 거부 검사는 있으나, 표식 하나와 미지정 빈 셀이 공존하는 문서의 전체 완료 오판은 검사하지 않는다.

총괄이 조사한 실제 누락 사례는 HWP 끝부분 BMC 9칸과 팀명·대표자·아이템명 3칸이다. 이 사례의 셀 편집 가능성은 총괄의 별도 실험 범위이며, 이 설계자는 실행하지 않았다. 이 문서는 특정 셀 편집 기법을 범용 HWP 지원으로 승격하지 않는다.

## 2. 선택

| 대안 | 얻는 것 | 비용·한계 | 판정 |
| --- | --- | --- | --- |
| SKILL 문구만 수정 | 가장 적은 코드 변경 | CLI `ok`만 보는 호출자와 회귀 검사에서 오판을 계속 허용 | 단독 적용 부족 |
| 전체 조사 워크플로 + 보수적인 완료 정보 + 해시 연결 목록 검사 | 현재 엔진을 유지하며 누락과 완료 과장을 직접 다룸 | 표식 없는 작성 대상의 발견·의미 판정은 에이전트/검수에 남음 | 선택 |
| 네 형식의 모든 칸을 자동 탐지·편집하는 새 엔진 | 자동화 범위를 크게 넓힐 수 있음 | 빈칸의 업무 의미·권한·첨부 요건을 구조만으로 결정할 수 없고 새 보존 위험이 큼 | 이번 수정에서 제외 |

선택의 핵심은 **실제 작성 범위는 넓히되, 현재 CLI의 편집 지원을 과장하지 않는 것**이다. 스킬은 부족한 영역을 준비본·문서별 검증된 편집 수단으로 보완한다. 보완할 수 없는 영역은 `blocked`로 남기고 이유를 설명한다. 지원하지 않는다는 이유로 조용히 범위에서 삭제하지 않는다.

포기하는 것: 이번 수정만으로 임의 문서의 전체 작성 대상을 자동 발견하거나, 일반 HWP 셀·스캔 PDF까지 편집한다고 보장하지 않는다. 동일 유형의 누락이 반복되고 안전한 원본/회귀 자료가 확보되면 별도의 adapter 기능으로 확대하는 결정을 다시 한다.

## 3. 스킬의 필수 워크플로와 책임

1. **원본 전체 조사.** 편집 전에 전체 페이지와 구조를 읽는다. 지원 필드 목록은 보조 자료다. 목차·머리말·본문·표·부록·별첨 양식·서명/확인 영역을 대조한다. 사람이 기입해야 하는 일반 빈칸, 안내 예문, `[작성]` 등도 찾는다. 추출 결과가 화면 전체를 설명하지 못하면 렌더 또는 지원되는 뷰어에서 확인한다.
2. **작성 대상 목록 확정.** 문서별 의미 있는 항목에 안정적인 ID와 원본 위치를 부여한다. 반복 표는 열 스키마와 실제 기록 수를 함께 기록한다. 편집용 표식 수를 전체 작성 대상 수로 쓰지 않는다. 이미 사실이 채워진 칸도 검토 후 유지/수정 대상임을 기록한다.
3. **사실과 범위 결정.** 기존 대화·자료를 재사용한다. 사용자 지시가 없으면 모든 적용 항목을 작성한다. 실제 문서에서 꼭 필요한 사실이 없으면 구체적으로 질문하고 다른 독립 항목을 진행한다. 가상 예시 요청이면 이름·역할·날짜·예산·일정·성과를 포함한 하나의 가상 설정을 먼저 만들고 적용한다.
4. **안전한 준비와 작성.** 원본을 보존하고 별도 준비본에 표식 등을 배치한다. 새로 발견된 영역도 채운다. 현재 CLI가 못 쓰는 영역은 이미 허용된 안전한 문서 편집 수단을 검토한다. 허용 범위 밖 작업이 필요하면 그 작업만 별도 제약으로 다룬다. 범용 엔진의 보존 검사를 제거해서 사례를 통과시키지 않는다.
5. **저장 후 전체 검수.** 최종 파일을 다시 열거나 읽고, 목록의 모든 적용 항목과 값·반복 행·첨부를 대조한다. 모든 페이지에서 잘림·겹침·빈 양식·잔여 안내 예문·문맥 불일치를 확인한다. 금액·인원·기간의 문서 내 합계를 확인한다. 최종 파일이 바뀌면 그 파일에 대한 검수 증거를 갱신한다.
6. **정확한 전달.** 단순 생성 성공과 전체 작성 확인을 구분한다. `blocked` 또는 전체 조사/렌더 미실행이 남으면 완성본이라고 부르지 않는다. 이번 과업에서는 검수된 작성 예시 하나씩만 비교본에 넣는다. 사용자에게 개발 중 짧은/긴 버전을 모두 최종 결과로 제시하지 않는다.

작성 대상 목록의 소유자는 문서를 작성하는 스킬/에이전트이다. CLI는 목록의 선언을 만들거나 업무상 제외를 결정하지 않는다. 최종 검수자는 원본과 최종 파일을 직접 대조하며, 가능하면 작성과 분리한다. CLI에 전달한 목록 자체를 누락 없음의 독립 증거로 사용하지 않는다.

## 4. 작성 대상의 상태와 근거

작성 대상은 아래 네 상태를 갖는다. 진행 중 미확인 항목은 `blocked`와 구체적인 원인으로 남긴다. 값이 확보됐다는 이유만으로 파일에 저장되기 전에 `filled`로 확정하지 않는다.

| 상태 | 허용 근거 | 금지되는 대체 판단 |
| --- | --- | --- |
| `filled` | 최종 파일의 해당 위치에서 유효한 값이 다시 읽히고, 필요한 경우 렌더에서 표시를 확인 | 입력 JSON에 값이 있음, 표식이 사라짐, 엔진 성공만으로 확정 |
| `explicitly_excluded` | 그 항목을 작성하지 말라는 사용자의 실제 지시와 그 지시의 범위/위치 | 에이전트가 어렵거나 길다는 이유로 제외, CLI 미지원이라 제외 |
| `not_applicable` | 원본의 적용 조건과 확인된 사실/가상 설정으로 해당 없음이 성립 | 모든 미확인 항목을 일괄 `해당 없음`, 허구의 면제 조건 |
| `blocked` | `missing-fact`, `unsupported-edit`, `unverified-output`, `missing-attachment`, `requires-authorized-signature` 등 원인과 필요한 다음 행동 | 공란을 그대로 두고 완료로 보고 |

고정 제목·표 머리글·일반 안내문·설명 페이지·장식용 여백은 작성 대상이 아니다. 다만 페이지별 비대상 판단을 기록하여 페이지 자체를 조사에서 빠뜨리지 않게 한다. 안내문 속 예문과 실제 입력 예시가 섞여 있으면 템플릿 문맥으로 구분한다. “빈칸이 아님”도 “작성 완료”도 자동 추정하지 않는다.

`not_applicable`은 문서가 허용하는 위치에 `해당 없음`과 짧은 이유를 표시하는 것을 원칙으로 하되, 해당 서식이 공란 유지나 항목 건너뛰기를 요구하면 그 규칙을 따른다. 서명·승인·접수번호 등은 실제 행위를 흉내 내지 않는다. 실제 문서는 권한 있는 당사자의 처리가 필요한 경우 `blocked`이다. 가상 예시는 서명 효력이 없는 예시임을 분명하게 표시하고, 실제 전자서명 완료를 주장하지 않는다.

부분 작성 요청도 원본 목록에서 사라지지 않는다. 요청 범위 밖 항목을 `explicitly_excluded`로 기록하며 보고는 “요청 범위 작성”으로 한다. 이미 받은 사용자 지시를 반복 확인하지 않는다.

## 5. 최소 CLI 계약

### 5.1 기존 계약 유지

- `fields`와 `checkValues`는 현재처럼 **발견한 지원 필드**의 타입·필수값·길이를 검사한다. 이 검사를 느슨하게 해서 공백을 통과시키지 않는다.
- `ok`는 명령 실행/파일 생성 성공을 뜻한다. 추가 `operation: "field-fill"` 또는 명확한 문서화로 의미를 고정한다.
- `inspect`에는 `fieldDiscovery: { scope: "explicit-fields", fullDocumentInventory: false }`를 추가하여 목록의 범위를 드러낸다.
- `validate`는 구조 검증이며 업무상 전체 작성 완료를 판정하지 않는다. 채운 최종 파일의 표식 0개도 전체 완성 증거가 아니다.

### 5.2 선택적 `--coverage FILE.json`

새 외부 서비스/DB 없이 작은 공통 모듈 하나가 목록의 일관성만 검사한다. `inspect`와 `fill`에 옵션을 연결한다. 옵션이 없다고 기존 필드 처리 사용을 막지는 않지만, 기본 전체 작성 범위의 확인 상태는 반드시 `incomplete`이다. 스킬은 그 파일을 중간 작업물로 취급하고 전체 작성·검수를 계속한다.

입력 형식의 제안:

```json
{
  "version": 1,
  "templateSha256": "<실제로 CLI가 읽는 준비본의 SHA-256>",
  "scope": "full",
  "slots": [
    {
      "id": "business.overview",
      "location": "원본 1쪽 / 사업 개요",
      "status": "filled",
      "evidence": { "kind": "fields", "fields": ["overview"] }
    },
    {
      "id": "bmc.partners",
      "location": "원본 5쪽 / BMC / 핵심 파트너",
      "status": "filled",
      "evidence": { "kind": "external-review", "reference": "최종 파일 셀 재읽기·렌더 검수 기록" }
    },
    {
      "id": "approval.signature",
      "location": "원본 2쪽 / 승인 서명",
      "status": "blocked",
      "reason": "권한 있는 당사자의 서명이 필요함"
    }
  ]
}
```

목록의 `status`는 호출자의 **선언**이다. 사전에 예정한 `filled`는 adapter의 실제 저장/재읽기 검사 후에만 엔진 검증 수에 반영한다. `external-review`는 호출자 선언으로 별도 집계하며, 입력에 `verified: true`를 써도 자동 검증으로 승격하지 않는다. 참조 문구를 명령이나 읽어야 할 경로로 실행하지 않는다.

검사할 내용:

1. 버전·객체·지원 enum·고유 ID·빈 값 아닌 위치·상태별 필수 근거를 검사한다. 임의의 상태/검증 플래그로 완료 등급을 올릴 수 없다.
2. `templateSha256`은 `inspectDocument`가 실제 읽은 bytes의 해시와 같아야 한다. 준비본이 한 글자 바뀌어도 새 목록으로 재검토한다. 원본 파일의 해시는 최종 검수 기록에서 별도로 보존하고, CLI가 확인하지 않은 원본 해시를 검증했다고 표시하지 않는다.
3. `evidence.kind: fields`의 필드 이름은 실제 발견 목록과 정확히 대응하고, 중복/미지 키를 거부한다. 발견 필드 전부가 적어도 하나의 명확한 대상에 연결돼야 한다. 반복 값은 기존 rows/columns 검사와 실제 기록 수 확인을 재사용한다.
4. `explicitly_excluded`는 사용자의 지시를 가리키는 근거가 필요하다. `not_applicable`은 조건과 이유가 필요하다. CLI는 그 근거의 진실성을 인증하지 않는다.
5. `scope` 기본은 `full`이다. `partial`은 사용자 요청 근거가 있어야 하며 응답에도 그대로 남는다. 부분 범위를 전체라고 바꾸지 않는다.
6. 새 모듈은 `manifest.json`의 등록 필드 스키마나 layout profile을 대체하지 않는다. 서로 다른 계약이다.

주의: 이번 최소 구현에서 제외 상태를 기록하는 기능은 각 adapter에 새로운 부분 편집 권한을 주지 않는다. 현재 필수 필드를 제외/공란 보존해야 하는 문서는 검증된 준비 방법이나 다른 허용 편집 수단으로 처리해야 한다. 그런 경로가 없으면 해당 범위는 `blocked`이다. `checkValues`의 빈 문자열 허용으로 우회하지 않는다.

### 5.3 응답: 선언 일관성과 전체 완성은 다르다

```json
{
  "ok": true,
  "operation": "field-fill",
  "completion": {
    "scope": "full",
    "status": "incomplete",
    "fullDocumentComplete": false,
    "inventory": "not-provided",
    "verificationScope": "explicit-fields",
    "reason": "문서 전체 작성 대상과 최종 표시를 확인하지 않았음"
  }
}
```

- 목록 없음 또는 `blocked` 있음: `completion.status: incomplete`.
- 목록의 선언·필드 대응이 일관되고 `blocked` 없음: `completion.status: requires-review`, `inventory: declared`, `verificationScope: explicit-fields-and-manifest-consistency`.
- 두 경우 모두 CLI의 `fullDocumentComplete`는 `false`이다. 이 CLI는 임의 문서의 전체 슬롯 탐지·전체 렌더 검수를 실행하지 않으므로 `complete`를 발급하지 않는다.
- 엔진이 채운 필드와 호출자가 외부에서 채웠다고 선언한 영역은 따로 집계한다. 후자는 자동 검증으로 세지 않는다.
- `templateSha256`과 발행 후 `outputSha256`은 기존대로 반환한다. 최종 검수 기록은 이 최종 해시와 원본/준비본/작성 대상 목록을 연결한다.
- CLI에서 생성됐지만 미완성인 파일은 스킬의 중간 산출물이다. 최종 응답에서 완성본처럼 링크만 던지고 끝내지 않는다. 최종 스킬 보고에서만 실제 전체 대조 근거를 기반으로 작성 범위의 완료 여부를 판정한다.

이 보수적인 계약은 악의 없이 목록을 한 항목으로 잘못 줄이거나 모든 항목을 임의 `not_applicable`로 선언해도 **CLI의 전체 완료 확인으로 바꿀 수 없게** 한다. 목록의 내용 진실성과 누락을 완전히 차단하는 기능은 아니다. 그 검사는 원본 전쪽 대조에 남으며 한계로 명시한다.

## 6. 실패·복구·동시성

| 상황 | 동작 | 복구 |
| --- | --- | --- |
| 목록 형식/상태/필드 대응 오류 | adapter 실행·발행 전에 `E_COVERAGE` 또는 기존 `E_INPUT`으로 거부 | 원본 조사와 필드 목록을 대조해 수정 |
| 준비본 해시 불일치 | `E_TEMPLATE_CHANGED`, 발행 없음 | 현재 준비본으로 위치/대상 재조사 |
| 유효한 목록에 미해결 항목 있음 | 지원 필드 처리 결과는 중간 파일로 생성 가능, `completion: incomplete` | 필요한 사실 확보·안전한 편집 보완·재검수 후 새 경로로 생성 |
| 현재 엔진의 입력/보존/배치 오류 | 기존 `E_FIELDS/E_PRESERVATION/E_LAYOUT` 유지 | 원본 보존, 해당 원인만 수정, 검사 약화 금지 |
| 값/서명이 불명확 | `blocked`, 해당 사실이나 권한이 필요함을 전달 | 확인되는 동안 독립 작업 진행 |
| 결과 생성 후 문서 변경 | 이전 검수 결과를 현재 결과의 증거로 사용하지 않음 | 최종 해시와 해당 항목/전체 배치 다시 검수 |

목록은 CLI 진입 시 한 번 읽은 객체를 검증하고 그 스냅샷으로 처리한다. 처리 도중 같은 경로를 다시 읽어 검증과 실행의 내용을 갈라놓지 않는다. 기존의 원본 재해시·덮어쓰기 방지·임시 파일 정리는 유지한다. 별도 DB/잠금 서비스를 추가하지 않는다. 로그와 오류에는 민감한 실제 입력값을 넣지 않고 대상 ID·위치·이유만 둔다.

## 7. 구현 순서와 소유 경계

1. `SKILL.md`와 `references/formats.md`에 전체 조사·네 상태·실제/가상 정책·최종 검수·단일 예시 전달 계약을 먼저 반영한다. 길어진 예시는 `references/full-document-completion.md` 같은 참조 하나로 분리할 수 있다.
2. 공통 `lib/coverage.mjs`를 최소 추가하고 `engine.mjs`의 inspect/fill 응답, CLI 옵션·오류 whitelist에 연결한다. adapter를 이 작업으로 범용화하지 않는다.
3. `tests/core.test.mjs` 또는 전용 coverage 테스트와 실제 CLI 반환 검사를 추가한다. 기존 필수값·보존·넘침 검사는 유지한다.
   CLI와 모든 adapter의 사용자 표시 문구도 함께 검사한다. 특히 `lib/adapters/pdf.mjs`의 이어쓰기 파일 inspect 경고인 '별지가 있는 완성 PDF입니다'는 '별지가 생성된 PDF입니다'처럼 관찰된 구조만 설명하도록 바꾼다. `completion.fullDocumentComplete: false`와 전체 완성 주장이 공존하지 않아야 한다. 이어쓰기 출력의 inspect를 실제 실행하는 회귀 검사로 이 문구와 완료 정보의 일관성을 확인한다.
4. 네 실제 문서를 원본 전체 목록으로 다시 작성한다. HWP 셀 등 문서별 추가 편집은 해당 사례 코드/자료 범위에서 보존·정확 값·렌더 증거를 남긴다. 이를 커버리지 검증기의 기능으로 주장하지 않는다.
5. 원본과 예시를 같은 정보구조로 다시 합본한다. 원본은 “원본 템플릿”, 결과는 “가상 작성 예시”를 모든 페이지에서 표시한다. 기존 문서 영역 밖에 표시해 양식을 가리지 않는다. 형식별 예시는 하나만 포함한다.
6. 빌드/패키지 검증을 실행한다. CLI가 `lib/vendor/runtime.mjs`를 우선 읽으므로 소스만 고치고 배포 엔진을 그대로 두지 않는다. `scripts/validate-package.mjs`의 소스 해시 검사와 두 ZIP의 실제 CLI 호출에도 완료 정보 회귀 검사를 넣는다.

이 설계자의 작성 소유 범위는 본 파일뿐이다. 구현·사례 파일·총괄 최종 기록은 수정하지 않았다.

## 8. 검증 시나리오

| ID | 입력/행동 | 관측할 결과 |
| --- | --- | --- |
| T1 | DOCX에 표식 1개와 표식 없는 필수 빈 셀 1개; 표식 값만 제공 | 파일 처리는 가능하나 전체 완료는 false/incomplete. 스킬 조사 목록에는 빈 셀도 포함. |
| T2 | HWP 현재 사례의 BMC·세 신원 칸을 목록에 포함 | 기존 본문 표식 처리가 끝나도 해당 셀 미작성 상태면 미완성. 실제 셀 채움 뒤 저장 후 값·렌더 대조. |
| T3 | 유효한 목록의 준비본 해시 한 글자 변경 | adapter 전에 `E_TEMPLATE_CHANGED`, 발행 파일 없음. |
| T4 | 중복 대상/필드·미지 필드·누락 필드·잘못된 상태·근거 없는 제외/해당 없음 | 일관성 오류, 기존 파일 보존. |
| T5 | 목록을 모든 `filled` 또는 모든 `not_applicable`로 자의적 선언 | 전체 자동 완료는 여전히 false. 외부 선언을 자동 검증 수에 넣지 않음. |
| T6 | 실제 문서에 금액/등록번호/서명 사실이 없음 | 임의 숫자·서명 대신 해당 항목 blocked. 구체적 필요한 사실만 질문. |
| T7 | 사용자가 한 부록만 제외한다고 이미 지시 | 그 부록만 제외 근거 기록, 나머지 모두 작성. 요청 범위 작성으로 표시. |
| T8 | 고정 안내문·장식 여백·설명 페이지 | 작성 대상으로 억지 포함/변형하지 않으며 페이지 조사 기록에는 남음. |
| T9 | 네 형식 가상 예시의 전체 목록과 최종 파일 | 이름·예산·기간·단위 일관, 미해결 필수 항목 0, 전 페이지 잘림/겹침/미지정 공란 검사. |
| T10 | 예시 합본을 처음 보는 사람이 목차·임의 중간 페이지 열기 | 현재 원본인지 가상 예시인지 바로 보임. 각 형식의 예시가 하나뿐임. |
| T11 | 소스와 배포 ZIP 각각 CLI 실행 | `inspect/fill/validate`의 범위 표시·완료 정보가 동일하고 vendor stale 검사 통과. |
| T12 | 생성된 이어쓰기 PDF에 inspect 실행 | 이어쓰기 구조만 설명하고 문서 전체 완성을 주장하는 경고가 없음. 전체 완료 미판정 정보와 문구가 일치. |

자동 테스트는 목록 일관성/해시/응답의 과장을 방지한다. T2/T6/T8/T9/T10의 의미·레이아웃은 실제 원본과 최종 문서 검수로 확인한다. 테스트의 숫자만으로 전체 사용자 과업을 통과시켰다고 하지 않는다.

## 9. 미확정과 인계

- **단일 예시 문서의 실제 적용 조건:** 각 원본 별첨이 해당 가상 조직/사업에 적용되는지 문서별 조사자가 확인한다. 미확인 항목을 일괄 비대상으로 두지 않는다. 확인되는 동안 그 밖의 본문·표는 작성 가능하다.
- **새 CLI 오류 이름:** 별도 `E_COVERAGE` 사용 또는 `E_INPUT` 재사용은 구현자가 일관된 오류 계약으로 정할 수 있다. 새 이름을 쓰면 CLI whitelist와 패키지 검사를 함께 고친다.
- **부분 편집 지원:** 이번 목록 기능은 adapter의 임의 필드 건너뛰기를 구현하지 않는다. 사용자가 제외한 기존 필드의 실제 보존 방법은 사례별로 확인해야 한다. 이를 지원하겠다고 새로 약속하지 않는다.
- **완전 자동 탐지:** 이번 수정으로 충족됐다고 말할 수 없다. 현재 사용자 요구는 스킬 전체 워크플로에서 원본 조사와 보완 편집까지 수행하여 충족해야 한다.
- **실행 상태:** 코드/테스트 파일과 기존 계약을 읽었다. 테스트·새 셀 편집 실험·빌드·배포는 실행하지 않았다. 다음 단계는 총괄의 독립 설계 검토 후 범위별 구현이다.
