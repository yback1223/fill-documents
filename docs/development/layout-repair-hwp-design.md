# HWP 입력 위치와 서식 보존 수정안

2026-10-08. 사용자 요구: 기존 형식을 유지/확장하고 문서의 목적에 맞는 내용으로 시험한다. 이전 장문 시험의 빈 문단 삽입을 중단한다.

## 관찰과 목표

- 원본 `wict-business-plan.hwp`의 실제 `○` 작성 문단은 공백/동그라미/본문의 글자 서식이 다르다. 원래 구현의 '문단 전체 균일' 제한 때문에 실제 입력 항목 대신 앞 빈 문단을 사용했고, 원래 항목이 미작성 상태로 남았다.
- 원본 0구역 8번 문단: 0부터 charShape 57(공백), 3부터 58(동그라미), 4부터 59(휴먼명조 12pt 본문). 이 마지막 본문 run에 표식을 넣고 204자 실제형 내용을 native replaceAll로 치환한 격리 실험에서 raw 글자서식 레코드 전체와 DocInfo 해제 바이트가 같았다. 대상 텍스트/줄·후속 세로 위치만 변경됐다.
- 쪽 테두리는 원본과 이전 최종 HWP의 모든 조사 페이지에서 같은 SVG 좌표/색으로 존재했다. PNG의 테두리 픽셀도 217/217/217로 확인했다. '테두리 소실'이라는 앞선 육안 판단은 철회한다. 제목/입력 항목 관계와 남는 빈 항목을 고친다.

## 좁은 구현 변경

1. 기존 preserve 경로의 균일 서식 조건은 유지한다. flow는 고유 표식을 포함하는 최상위 텍스트 문단에서 **표식 시작부터 문단 끝까지 하나의 같은 글자서식**이면 고정 접두부의 혼합 서식을 허용한다. 표식이 서로 다른 run을 가로지르거나 중간/끝에 다른 서식이 나타나면 계속 거부한다.
2. raw CHAR_SHAPE 레코드는 8바이트 배수, 첫 위치 0, 엄격 증가, 모든 변경 지점이 첫 표식 시작 이하인 경우만 허용한다. 따라서 원래 글자서식 위치/ID를 그대로 보존할 수 있다. 필드 안에 있는 텍스트에 다른 서식을 적용하지 않는다.
3. 후보 재읽기 시 접두부는 원본 각 문자 서식과 exact, 교체된 나머지는 원본 tail 서식과 exact인지 검사한다. 기존 PARA_HEADER, PARA_TEXT, LINE_SEG만 허용하는 원시 변경 검사는 유지한다. CHAR_SHAPE 레코드/DocInfo를 재작성하거나 완화하지 않는다.
4. 페이지 검사는 입력 필드 외에도 문서 전체의 비어 있지 않은 본문 run이 물리 페이지 안에 있는지 확인한다. 원래 허용된 음수/장식 위치가 있으면 실패를 숨기지 않고 위치를 보고한다. 이는 겹침·문단 관계·원본 앱 검사 대체가 아니다.

## 템플릿 준비/실제형 시험

- 원본은 그대로 두고 새 준비본에서 실제 동그라미 문단 뒤에 표식을 추가한다. 기존 공백/동그라미/본문의 글자서식·글자 크기는 유지한다. 제목/아이템명도 원래 위치에 입력한다.
- 창업 배경, 목표, 선정 동기, 기능, 효과, 팀, 기술 계획, 시장 가설, 실행/자금/사업모델/파급효과를 서로 다른 가상 내용으로 채운다. 조사·계약 실적은 꾸며 확정하지 않고 검증 계획과 목표로 쓴다.
- 짧은/상세 사례 모두 반복 문장을 사용하지 않는다. 상세 사례는 각 기존 항목의 설명이 늘어나 자연스럽게 다음 쪽으로 이어지도록 한다.
- 본문 외 BMC 표는 별도 지원/검사 필요이며 이를 채웠다고 보고하지 않는다. 이 한계는 성공 판정과 결과 설명에 남긴다.

## 검증 조건

- 기존 혼합 서식 거부 반례 중 placeholder 자체가 혼합이거나 그 뒤 다른 서식이 있는 경우는 계속 실패.
- 고정 접두부+균일 tail 치환 성공, 문자별 서식/CHAR_SHAPE/비대상 스트림 exact.
- 실제 입력 문단을 모두 다시 읽고 값이 그대로이며 원래 ○가 빈 채 남지 않음. 선택 본문 밖 영역은 원본 보존.
- 최종 저장 파일을 다시 열어 모든 페이지 PNG를 생성하고, 빈 페이지/겹침/잘림/고아 제목/글자 간격을 직접 검수. 작성 중 미저장 native view와 최종 재열기 화면은 구분한다.

격리 실험: `문서서식-재검증-20261008/scripts/probe-hwp.mjs`. 현재 문서는 설계이며 생산 구현/인수 통과를 의미하지 않는다.
